# Security model

**This is a development-only toolkit. Do not run it anywhere that matters.**

## Why MCP access here is privileged

Connecting Claude Code to this site hands it the abilities MS WP Abilities
registers, executed as a WordPress **administrator**. That includes:

- creating, editing, publishing and trashing any post or page
- creating categories and tags
- updating media metadata
- reading the user list
- reading site settings
- **installing plugins from wordpress.org, and activating them**
- **updating plugins and themes**
- **`rest-write` — arbitrary POST/PUT/PATCH/DELETE against any registered REST route**

Installing and activating a plugin is arbitrary code execution inside the
WordPress container. `rest-write` reaches anything any plugin has registered.
Treat the MCP endpoint as equivalent to handing over the admin password.

MS WP Abilities hard-blocks four things in `mswpa_rest_write_blocked_reason()`
regardless of what the agent asks for: writes to `/wp/v2/users`, `DELETE` on
`/wp/v2/plugins`, writes to `/wp/v2/settings`, and any `force=true` permanent
delete. That is a short list of especially destructive routes, not a general
safety net. Read it in the plugin source before relying on it.

## Conversational confirmation is not a security boundary

MS WP Abilities uses a two-step model for content updates
(`preview-post-update` → `apply-post-update`) and asks the agent to state the
proposed REST write before calling `rest-write`. Both are instructions in the
ability descriptions. The code does not verify that a human saw or approved
anything — it only checks that a preview was staged, by the same user, within
ten minutes.

So:

- A model that skips the confirmation step still gets the write through.
- Prompt injection — a post body, a plugin readme, a REST response containing
  instructions — reaches the same agent that holds the credential.
- "Claude will ask first" is a working convention between you and the agent, not
  an enforced control.

The enforced controls are WordPress capability checks, the hard-block list, and
the fact that nothing outside your machine can reach the endpoint.

## Application Passwords

MCP requests authenticate with a WordPress **Application Password**, not the
administrator's login password:

- generated by WordPress, shown exactly once, revocable independently
- scoped to one user, labelled (`claude-code-mcp`), visible and revocable in
  **Users → Profile → Application Passwords**
- stored in `.secrets/application-password` (git-ignored) and in Claude Code's
  own `~/.claude.json`, outside this repository
- `./bin/setup` keeps `.secrets/` at mode `0700` and `.env` /
  `application-password` at `0600` where the filesystem enforces Unix modes

Revoke it at any time:

```bash
docker compose exec -T wordpress wp-app-password delete
rm -rf .secrets
./bin/connect --remove
unset WORDPRESS_MCP_BASIC_AUTH   # if you exported it from --print
```

`./bin/connect --print` writes the live Basic auth header to stdout (needed for
Codex / Cursor). Treat that output as a secret: do not paste it into tickets or
logs, and clear it from shell history on shared machines. `claude mcp add
--header` also puts the header on the process argv briefly; do not run connect
on a multi-user host you do not trust.

WordPress refuses Application Password authentication over plain HTTP unless the
site is a local environment, so `wp-config.php` sets
`WP_ENVIRONMENT_TYPE = 'local'`. **That is the single reason this works over
`http://`, and it is also the reason this setup must never be reachable from
anywhere else.** No authentication is disabled: an unauthenticated request to the
MCP endpoint gets HTTP 401, and `tests/integration.sh` asserts both that and the
rejection of a wrong password on every run.

## Localhost binding

Both published ports bind to the loopback address:

```yaml
ports:
  - "127.0.0.1:${WP_PORT:-8080}:80"      # wordpress
  - "127.0.0.1:${DB_PORT:-3307}:3306"    # db
```

Not `0.0.0.0`. Nothing else on your network, and nothing on the internet,
reaches either service. `tests/smoke.sh` asserts the binding, so a change that
widened it would fail CI.

Things that would break this and must not be done:

- changing the bindings to `0.0.0.0` or omitting the host part
- publishing the same ports from a `docker-compose.override.yml`
- setting `network_mode: host` (Compose ignores `ports` and binds all interfaces)
- tunnelling the port (ngrok, Cloudflare Tunnel, `ssh -R`)
- running this on a shared or public host
- putting a reverse proxy in front of it

`./bin/setup` and `./bin/status` refuse any Compose publish whose `host_ip` is
not `127.0.0.1`, and refuse `network_mode: host`, including overrides.

## Why credentials are excluded from Git

`.gitignore` excludes `.env`, `.secrets/`, `.mcp.json`,
`.claude/settings.local.json`, `*.sql`, `*.pem`, `*.key` and the generated
WordPress state. The tracked `.env.example` carries `CHANGE_ME` placeholders;
`./bin/setup` replaces each with a random 32-character secret, in `.env` only.

The repository itself is private, but a private repository is not a secret
store: it is cloned, shared, forked, backed up and read by CI. A committed
credential is a credential you have to rotate, whatever the repository's
visibility.

CI re-checks this on every push — the workflow fails if a tracked file matches a
credential pattern, or if `.env`, `.secrets/` or a `.sql` dump ever appears in
`git ls-files`.

## Download integrity

Pinned MCP Adapter and MS WP Abilities release ZIPs are SHA-256-checked by
`wp-provision` before install. The `wp-cli/ability-command` tarball is
SHA-256-checked in the Docker image build (same pattern as the WP-CLI phar's
SHA-512). Digests live next to the version pins in `.env.example`.

## What this setup deliberately does not do

- It does not disable WordPress authentication, nonces or capability checks.
- It does not add an unauthenticated endpoint.
- It does not widen the MCP Adapter's default permission callbacks.
- It does not mark any extra ability public. The public set is whatever MS WP
  Abilities and the adapter ship.
- It does not install a plugin whose job is to bypass something.

If a future change to this repository needs any of the above to make an
integration work, the integration is wrong.

## If you want it stricter

The MCP Adapter exposes capability filters. Dropping this in a must-use plugin
raises the bar on the meta-tools:

```php
add_filter( 'mcp_adapter_execute_ability_capability', fn() => 'edit_posts' );
```

You can also connect as a lower-privileged user: create an editor, issue the
Application Password on that account, and set `WP_ADMIN_USER` accordingly. The
abilities' own permission callbacks then refuse plugin installs and theme
updates on their own.
